# BattleBlaster 局域网穿透需求文档

> 版本: v0.1  
> 状态: 需求设计稿，尚未实现  
> 最后更新: 2026-06-09  
> 相关文档: `Docs/06-network-mode-developer-guide.md`, `Docs/network-module-implementation-plan.md`, `Docs/09-nat-traversal-developer-guide.md`

## 1. 背景

BattleBlaster 当前联网能力以 LAN Listen Server 为主: 房主在本机开启 `OpenLevel(Map?listen)`，其他玩家通过 `IP:Port` 加入。这条路径适合同一局域网或已经完成端口映射的环境，但离开局域网后会遇到 NAT、防火墙、运营商网络、校园网、移动热点等限制。

目标新增一个并列的联网入口:

```text
联网游戏
├─ 局域网联机
├─ 局域网穿透
└─ 权威服务器
```

其中“局域网穿透”使用一台有公网 IP 的云服务器作为中转节点。玩家不需要在路由器上配置端口转发，也不需要处在同一局域网。房主仍然在本机运行 Listen Server，云服务器只负责房间注册、连接协调和 UDP 数据中转。

## 2. 产品定位

局域网穿透不是 Dedicated Server，也不是完整匹配系统。它的定位是:

- 让普通玩家可以像 LAN 一样开房，但邀请外网朋友加入。
- 使用公网云服务器提供稳定入口，避免依赖同一局域网。
- 房主本机仍然承担游戏服务器权威逻辑，云服务器不运行 UE 对局。
- 首版以房间码加入为核心，不做公开大厅和自动匹配。

三种联网入口的区别:

| 入口 | 服务器权威位置 | 玩家加入方式 | 适用场景 | 首版状态 |
| --- | --- | --- | --- | --- |
| 局域网联机 | 房主本机 Listen Server | 输入 LAN IP:Port | 同一局域网、开发测试 | 已有基础实现 |
| 局域网穿透 | 房主本机 Listen Server，云端只中转 | 输入房间码或中转地址 | 外网好友房、无路由器权限 | 本文规划 |
| 权威服务器 | 云端 Dedicated Server | 输入服务器地址，后续可扩展列表 | 长期开服、公平性更强 | 后续规划 |

## 3. 目标用户

- 想和朋友远程联机，但不会配置路由器端口映射的玩家。
- 使用校园网、出租屋网络、移动热点、运营商 NAT 的玩家。
- 开发测试阶段需要跨网络验证 Listen Server 的开发者。
- 暂时不需要长期 Dedicated Server，只需要“开一局、朋友进来”的轻量房间体验。

## 4. 用户体验目标

### 4.1 房主体验

1. 主菜单进入 `联网游戏`。
2. 选择 `局域网穿透`。
3. 选择 `创建房间`。
4. 设置玩法模式、地图、人数、AI 数量、目标分数、端口等对局参数。
5. 点击 `开始房间`。
6. 游戏显示房间码、中转状态和可复制邀请信息。
7. 好友输入房间码后加入对局。

房主不应该需要:

- 登录云服务器后台。
- 配置路由器端口转发。
- 知道自己的公网 IP。
- 手工启动额外命令行工具，除非这是开发阶段的临时方案。

### 4.2 加入者体验

1. 主菜单进入 `联网游戏`。
2. 选择 `局域网穿透`。
3. 选择 `加入房间`。
4. 输入房间码或邀请信息。
5. 客户端自动获取中转地址并连接。
6. 进入房主的 Listen Server 对局。

加入者不应该需要:

- 知道房主的 LAN IP。
- 知道房主的公网 IP。
- 处在同一局域网。
- 修改系统网络设置。

## 5. 功能需求

### 5.1 联网入口

- 网络模式选择页需要最终呈现三个并列选项:
  - `局域网联机`
  - `局域网穿透`
  - `权威服务器`
- `局域网联机` 继续使用现有 LAN Host / Join 流程。
- `局域网穿透` 进入独立菜单，不复用 LAN 文案。
- `权威服务器` 保持独立规划，不应和局域网穿透混在同一个按钮里。

### 5.2 创建穿透房间

房主创建房间时需要支持:

- 选择网络玩法模式: Deathmatch / TeamDeathmatch / MOBA / TeamMOBA。
- 选择地图。
- 设置最大玩家数。
- 设置 AI 数量。
- 设置目标分数。
- 设置本地 Listen Server 端口，默认沿用 `7777`。
- 连接云端中转服务。
- 生成房间码。
- 显示房间状态:
  - 正在连接中转服务
  - 中转服务已连接
  - 等待玩家加入
  - 中转异常
  - 房间已关闭

房间创建成功后，房主本机仍然以 Listen Server 方式进入地图。

### 5.3 加入穿透房间

加入者需要支持:

- 输入房间码。
- 可选输入房间密码。
- 请求云端控制服务解析房间。
- 获取临时中转端点。
- 自动通过中转端点加入房主的 Listen Server。
- 在连接失败时显示明确原因。

常见失败原因:

- 房间码不存在或已过期。
- 房间已满。
- 房主已离开。
- 云端中转服务不可用。
- 本地网络阻断 UDP。
- 客户端版本或协议版本不兼容。

### 5.4 云端守护进程

云服务器需要运行 24 小时待命的守护进程，职责包括:

- 提供健康检查。
- 创建和销毁房间。
- 维护房主心跳。
- 分配房间码。
- 分配 UDP 中转端口或通道。
- 管理加入者临时连接。
- 转发 UE 游戏 UDP 数据。
- 限制速率，避免开放中转被滥用。
- 记录必要运行日志。

守护进程不负责:

- 运行 UE Dedicated Server。
- 判定游戏胜负。
- 存储玩家长期数据。
- 做反作弊裁决。
- 做公开大厅和匹配。

### 5.5 房间码

首版使用短房间码作为邀请入口。

要求:

- 房间码应短、易读、大小写不敏感。
- 房间码应有过期时间。
- 房间码不能直接暴露云端内部令牌。
- 客户端通过房间码换取临时中转信息。

建议:

- 6 到 8 位字母数字组合，例如 `B7K2Q9`。
- 房间创建后显示可复制文本，例如 `房间码: B7K2Q9`。
- 开发阶段可同时显示 `RelayIP:Port`，正式 UI 优先隐藏低层地址。

### 5.6 房间生命周期

房间状态:

| 状态 | 含义 |
| --- | --- |
| Creating | 房主正在请求云端创建房间 |
| WaitingHostTunnel | 云端已创建房间，等待房主中转通道连上 |
| Open | 房间可加入 |
| InGame | 至少一名加入者已进入，房间处于游戏中 |
| Closing | 房主主动关闭或游戏返回主菜单 |
| Expired | 房主心跳超时或房间超过最大生命周期 |
| Error | 云端或本地中转异常 |

规则:

- 房主离开后，房间关闭。
- 房主网络断开超过心跳超时后，房间关闭。
- 房间关闭后，加入者应断线或返回主菜单。
- 房间最大生命周期首版建议 4 小时，避免长期占用端口。
- 未开始对局的空房间建议 10 分钟无心跳后回收。

### 5.7 连接质量展示

局域网穿透菜单和对局内应能展示基本连接状态:

- 中转服务连接状态。
- 当前加入人数。
- 房主到中转服务器延迟。
- 本地客户端到中转服务器延迟。
- 可选显示丢包率。

首版最低要求:

- 房主能看到“中转已连接 / 中转断开”。
- 加入者连接失败时能看到明确错误。

## 6. 非功能需求

### 6.1 性能

目标云服务器规格: 2 核 CPU、2 GB 内存、40 GB 磁盘。

这台机器适合做轻量房间中转，但容量主要受公网带宽限制，而不是磁盘。首版容量目标应保守:

- 支持少量好友房并发。
- 每个房间优先按 2 到 4 名真人玩家验证。
- 以游戏实际带宽压测结果决定正式并发上限。
- 不承诺大量公开房间同时运行。

性能目标:

- 中转进程常驻内存应远低于 2 GB。
- 单房间额外中转延迟应尽量低，目标是只增加一个云端转发跳点。
- 中转服务不能对 UE 游戏包做复杂业务解析。
- 数据面应避免频繁磁盘写入。

### 6.2 稳定性

- 守护进程崩溃后应能由系统服务自动拉起。
- 守护进程重启后旧房间可以全部失效，客户端需要给出可理解错误。
- 日志应能定位房间创建、加入、心跳、端口分配、异常断开。
- 房间和通道必须有 TTL，避免僵尸房间长期占资源。

### 6.3 安全

局域网穿透不能变成任意 UDP 转发器。

最低要求:

- 只有通过控制服务创建的房间可以占用中转资源。
- 加入者必须先通过房间码换取临时中转入口。
- 房间令牌和加入令牌必须有过期时间。
- 每房间限制最大玩家数和最大带宽。
- 对异常包、超大包、高频包做丢弃和限速。
- 不提供任意目标 IP / Port 的转发能力。
- 云端只允许转发到已注册房主通道。

推荐要求:

- 控制面使用 HTTPS。
- 令牌使用随机数或 HMAC 签名。
- 房间可选密码。
- 日志不记录玩家个人敏感信息。
- 云服务器防火墙只开放必要端口。

### 6.4 兼容性

- 不改变现有 LAN Listen Server 的玩法逻辑。
- 不复制 Deathmatch / TeamDeathmatch / MOBA / TeamMOBA 游戏规则。
- 局域网穿透只是连接方式差异。
- 进入对局后继续复用现有 `Modes/Network` 的服务器权威实现。
- 现有 `FNetworkMatchSettings` 中的玩法参数仍然作为对局配置来源。

## 7. 首版范围

### 7.1 必做

- 新增 `局域网穿透` 产品入口设计。
- 云端守护进程需求定义。
- 房主创建房间。
- 加入者输入房间码加入。
- UDP 游戏数据经云端中转。
- 房主本机 Listen Server 保持权威。
- 房间 TTL、心跳、关闭、基础限速。
- 跨两个不同公网环境完成联机验收。

### 7.2 暂不做

- 完整公开房间列表。
- 自动匹配。
- 排位和账号系统。
- 云端 Dedicated Server 自动开服。
- NAT 类型检测和 UDP 打洞直连优化。
- 断线重连。
- 跨区域中转节点选择。
- 复杂反作弊。
- 商业级 DDoS 防护。

## 8. 验收标准

### 8.1 产品验收

- 主菜单联网入口能清楚区分 `局域网联机`、`局域网穿透`、`权威服务器`。
- 房主在没有路由器端口映射的家庭网络中可以创建穿透房间。
- 加入者在另一套网络中可以通过房间码加入。
- 加入者不需要知道房主 IP。
- 房主关闭房间后，加入者不能继续通过旧房间码加入。
- 房间码错误、房间过期、服务不可用时都有明确提示。

### 8.2 技术验收

- LAN Host / Join 不受影响。
- 局域网穿透进入对局后复用现有网络 GameMode。
- Deathmatch 至少能完成移动、开火、命中、死亡、复活、计分、结算。
- TeamDeathmatch / MOBA / TeamMOBA 不因连接方式变化引入新规则分支。
- 云端守护进程能 24 小时运行，并通过健康检查确认存活。
- 房间超时后资源被回收。
- 云端日志能追踪一次创建房间、加入房间、关闭房间的完整链路。

## 9. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 云服务器公网带宽不足 | 延迟、丢包、并发低 | 首版限制房间数和人数，先做压测 |
| UDP 被本地网络阻断 | 部分玩家无法加入 | 后续提供 TCP/WebSocket 兜底或提示更换网络 |
| Host Listen Server 仍可作弊 | 公平性弱于 Dedicated Server | UI 和文档中明确该模式是好友房方案 |
| Relay 被滥用成公开转发器 | 安全和费用风险 | 房间令牌、端口 TTL、限速、非任意转发 |
| UE UDP 连接对源地址敏感 | 简单转发可能无法多客户端加入 | 开发实现必须保留每个远端客户端的独立映射 |
| 云端重启导致房间失效 | 游戏中断 | 首版接受，客户端给出清晰错误 |

## 10. 命名建议

产品 UI 可以使用:

- `局域网联机`
- `局域网穿透`
- `权威服务器`

技术内部建议使用更准确的命名:

- `LAN`: 局域网直连。
- `Relay`: 公网中转穿透。
- `DedicatedServer`: 云端权威服务器。

不要把 `Relay` 命名成 `DedicatedServer`，因为它不运行 UE 对局，也不承担游戏规则权威。
